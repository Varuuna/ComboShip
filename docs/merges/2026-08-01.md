## Why the line switch

Every Harbour Masters port tracks `port-maintenance`; ComboShip alone tracked `main`. See the
standing-policy section in [../UPSTREAM_MERGES.md](../UPSTREAM_MERGES.md). Pre-flight confirmed the
switch is lossless: `main`'s only non-refactor commits (#1112, #1127) already exist on
`port-maintenance` as re-lands (`8a67fa4b9`, `026bbc278`), and its other 8 commits all postdate our
old pin by 6-7 weeks, so nothing here consumed them. #1127 touched a LUS CI workflow we don't even
vendor.

## Tooling fixes (scripts/upstream-merge.ps1)

- **`git mktree` via a PowerShell pipe appended CRLF**, so the vendor commit's tree entry was
  literally named `libultraship\r` and every merge path came back `invalid path 'libultraship?/...'`.
  Windows-only — CI runs the script on Ubuntu where the line ending is bare `\n`. Replaced with the

- **A failed merge was reported as "clean"** (the script only checked for `U`-state files, and a

## The silent mis-merge (Context) — the important one

Git reported `Context.h`/`Context.cpp` as **auto-merged with no conflict** and produced code that
could not compile: two `GetRawInstance()` definitions, `.lock()` called on a `unique_ptr`, and
`SetInstance(shared_ptr)` assigning into a `unique_ptr`. It had silently interleaved two
incompatible ownership designs.

`port-maintenance` fully landed **#1103**: libultraship owns the `Context` via `std::unique_ptr`,
and `GetInstance()`/`SetInstance()` no longer exist. Our tree had deliberately refused that to keep
shared_ptr refcounting. **We adopted upstream's model**, because SoH itself was already 405-to-16 in
favour of `GetRawInstance()` — we were the outlier, and staying divergent meant re-fighting the
most-touched LUS file every pass.

- Reset `Context.{h,cpp}` to upstream, re-adding only `SetResourceManager()` (per-game RM swap;
  upstream has no equivalent and it is load-bearing for OOT↔MM).
- Converted ~72 `Ship::Context::GetInstance()` sites (soh 16 / mm 17 / combo 25 / LUS 14). Only the
  `Ship::`-qualified form was rewritten — soh's randomizer has its own unrelated `Context` class.
- Fixed two `ctx.get() == mCtx` identity checks in `ResourceManagerScope` / `OwnRMScope`.
- Fixed two latent `context->GetInstance()->GetWindow()` static-via-instance calls
  (`OTRGlobals.cpp`, `BenPort.cpp`) that only compiled while `GetInstance()` existed.
- `OTRGlobals::context` and `OTRGlobals` (mm) `context` are now raw `Ship::Context*`.
- **Teardown changed shape:** both games previously released a `shared_ptr` and soh's drop destroyed
  the Context implicitly. soh's `DeinitOTR` now calls `Ship::Context::DestroyInstance()` explicitly,
  at the same point. MM_Deinit-before-SOH_Deinit ordering is unchanged and still required.
  **This is the main playtest risk of this pass** — see [../deviations/boot-shutdown.md](../deviations/boot-shutdown.md).

## Post-merge bug: dropped the console-redirect guard (found in playtest)

X-closing on the OOT file select asserted in `ucrt\src\appcrt\lowio\write.cpp:50`
(`fh >= 0 && (unsigned)fh < (unsigned)_nhandle` — a write to a closed file descriptor). X-closing
immediately after boot did not.

Cause: `Context.cpp` was reset to upstream wholesale after auditing only `Context.h`'s markers, which
dropped the `&& !defined(COMBO_BUILD)` on upstream's Debug/Windows `FreeConsole()` + `AllocConsole()`
+ stdout `freopen` block. Every module shares one UCRT under `/MD`, so re-enabling that redirect in
soh.dll invalidates the file descriptors the launcher's console already owns; the next write through
a stale `fh` trips the CRT handle check. Restored the guard.

**Method note for future passes:** the deviation set of a vendored file is
`diff <old-upstream-tree> <our-pre-merge-tree>` — *not* the file's `ComboShip:` comments (this one
had a marker, but an uncommented deviation would have been invisible), and *not* a diff against the
**new** upstream (that mixes our deviations with upstream's own changes). Also note
`scripts/upstream-merge.ps1` rebuilds `vendor-<name>` on **every** invocation, so after more than one
run `vendor-<name>~1` is no longer the old upstream — resolve the old tree by SHA
(here `25ca23704`). Re-audited every LUS file this way afterwards; the console guard was the only
casualty. `GfxDebuggerWindow.cpp` also carried our #1141 hand-port (the `SETTILESIZE_INTERP`/`LERP`
debugger cases) and taking it wholesale was safe only because upstream now has them.

## RESOLVED (not a regression): MM HUD A button missing

The A button vanishing on OOT→MM was **not caused by this merge**. It is a pre-existing 2Ship bug
that fires whenever the *rendered game area* is narrower than 4:3, and it reproduces identically on
`develop`. `mm/2s2h/BenPort.cpp`, `mm/src/code/z_parameter.c` and `mm/2s2h/BenGui/HudEditor.cpp` are
byte-identical between `65a26f694` (pre-merge) and the merged tip.

Root cause, in `OTRConvertHUDXToScreenX` (`mm/2s2h/BenPort.cpp`):

```c
uint32_t gameWidth;                            // e.g. 1045
int32_t  hudWidth = gameHeight * (4.0f/3.0f);  // e.g. 1012 * 1.333 = 1349
float gameOffset = (gameWidth - hudWidth) / 2; // unsigned: wraps to ~2147483520
```

`gameWidth` is `uint32_t`, so once `hudWidth > gameWidth` the subtraction wraps and the ~2.1e9
offset swamps the real coordinate. Only the A button breaks because it is the one HUD element that
feeds converted coordinates into a **viewport** (`Interface_SetPerspectiveView`); B/C route theirs
through scissors and texture rects, which clamp. Both the vanilla and HUD-editor branches call the
converter, so the HUD-editor mode is irrelevant.

**Trigger is window geometry, not config corruption.** Docked ImGui windows (CheckTracker,
ItemTracker, AnchorRoom, Notifications) shrink the game viewport below 4:3 — measured 1045x1012,
aspect 1.03. Widening the window restores the A button immediately. Deliberately **not** reported
upstream (user call, 2026-08-01): it is a non-issue in practice and has an obvious workaround.

**Why it looked like a regression.** The comparison `develop` build was a *fresh download with a
fresh config* — default 16:9 window, no docked trackers, so it stayed above 4:3. The working build
carried the existing `comboship.json`. Same binary behaviour, different geometry.

**Lesson for the next bisect:** before bisecting a "regression" found by comparing two builds,
confirm both builds share a config and window state. A fresh-download baseline is not a controlled
comparison. Roughly a dozen builds were spent bisecting LUS commits for a bug that was never in LUS;
the mechanism-first diagnostic (printf the element's own inputs) found it in two builds. Also note
`HudEditor_ShouldOverrideDraw()` is not re-callable for diagnostics — the override branch resets
`hudEditorActiveElement` to `NONE`, so a later call returns a misleading `false`.
